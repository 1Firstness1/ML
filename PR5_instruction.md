## 1. Сначала: какой у тебя Mac?

🍎 **MAC**
```bash
uname -m
```

- `arm64` → **Apple Silicon (M1/M2/M3/M4)**.
- `x86_64` → Intel.

### Вариант A — Intel Mac
Всё как в методичке: VirtualBox 7.x и образ **`ubuntu-24.04.x-live-server-amd64.iso`** (https://ubuntu.com/download/server). Если при запуске ВМ пишет «Kernel driver not installed» — `Системные настройки → Конфиденциальность и безопасность` → разрешить ПО Oracle, перезагрузить Mac.

### Вариант B — Apple Silicon ⚠️
VirtualBox на M-чипах (версия **7.1 и новее**, отдельная сборка «macOS / Arm64») умеет запускать **только ARM-гостей**. Образ amd64 из методички **не запустится**. Нужно:

1. VirtualBox 7.1+ именно для macOS/Arm (https://www.virtualbox.org/wiki/Downloads);
2. образ **Ubuntu Server 24.04 LTS для ARM64**: `ubuntu-24.04.x-live-server-arm64.iso` (https://ubuntu.com/download/server/arm);
3. в мастере ВМ тип **Linux / Ubuntu (ARM 64-bit)** вместо «64-bit».

Остальные шаги идентичны. Отличия, которые могут встретиться: имена сетевых интерфейсов (вместо `enp0s3/enp0s8` могут быть другие — ориентируйся на вывод `ip -brief address`, адреса `10.0.2.x` = NAT, `192.168.56.x` = Host-only) и чуть другой внешний вид мастера. Резервный вариант из методички (готовый OVA от кафедры) на ARM-Mac, скорее всего, не подойдёт, так как собран под x86 — напиши преподавателю заранее.

В отчёте обязательно упомяни, что образ ARM64, и объясни почему (одна строка в «Выводах»).

## 3. Задание 1. Учётная запись и ключевая аутентификация

### Шаг 1.1 — создать пользователя `devops`

🍎 **MAC**
```bash
ssh student@127.0.0.1 -p 2222
```
🖥 **VM** (в этой сессии)
```bash
sudo adduser devops
sudo usermod -aG sudo devops
groups devops
```
`adduser` спросит пароль (**запиши**; пригодится для `sudo`) и необязательные поля (Enter, Enter…). В выводе `groups devops` должно быть `devops : devops sudo`.

**Проверка отпечатка ключа хоста** (то, ради чего существует `known_hosts`). 🖥 **VM**:
```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```
Сравни `SHA256:...` с тем, что клиент показывает при первом подключении `ssh ... (ED25519 key fingerprint is SHA256:...)`. При работе с удалённым сервером это **единственный** способ убедиться, что ты подключился к настоящему серверу, а не к подмене.

> Эту проверку проще всего показать так: отдельно подключись `ssh student@127.0.0.1 -p 2222` **с чистым known_hosts** (`ssh-keygen -R "[127.0.0.1]:2222"`), сравни отпечаток и сделай скриншот. Не обязательно, но красиво и усиливает ответ на вопрос 9.

### Шаг 1.2 — ключевая пара (на Mac)

🍎 **MAC**
```bash
ssh-keygen -t ed25519 -C "devops-vm-key" -f ~/.ssh/devops_vm
```
Passphrase — просто Enter (дважды). Если поставить фразу, при каждом входе будет запрос, что сломает «вход без запроса пароля» для скриншотов.

Не используй ключ от GitHub из работы № 1 — отдельная пара для отдельной цели (компрометация сервера не должна открыть репозитории).

Появятся два файла: `~/.ssh/devops_vm` (**закрытый**, никому не показывать!) и `~/.ssh/devops_vm.pub` (открытый).

### Шаг 1.3 — положить открытый ключ на сервер

🍎 **MAC**
```bash
ssh-copy-id -i ~/.ssh/devops_vm.pub -p 2222 devops@127.0.0.1
```
Запросит пароль `devops` (в последний раз). Если `ssh-copy-id` недоступна, эквивалент:
```bash
cat ~/.ssh/devops_vm.pub | ssh -p 2222 devops@127.0.0.1 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```
Если `Permission denied, please try again` — неверно введён пароль; сбрось на сервере (под `student`): `sudo passwd devops`.

### Шаг 1.4 — проверка входа по ключу и прав

🍎 **MAC**
```bash
ssh -i ~/.ssh/devops_vm -p 2222 devops@127.0.0.1
```
Пароль запрашиваться **не должен**. Затем 🖥 **VM** (уже внутри):
```bash
stat -c '%a %n' ~/.ssh ~/.ssh/authorized_keys
```
Ожидается:
```
700 /home/devops/.ssh
600 /home/devops/.ssh/authorized_keys
```
Если запрос пароля всё же есть — права слишком широкие (должно быть 700 и 600), `sshd` молча отклоняет ключ («bad ownership or modes»).

> 📸 **S11 (обязательно)** — вывод `stat` с `700` и `600`.
> 📸 **S12 (обязательно)** — вход `ssh -i ~/.ssh/devops_vm -p 2222 devops@127.0.0.1` без запроса пароля (видно приглашение `devops@devops-vm`).
> *Подпись:* «Вход по ключу без пароля. Права 700 для ~/.ssh и 600 для authorized_keys — условие приёма ключа службой sshd».

### Шаг 1.5 — зафиксировать методы аутентификации

🍎 **MAC**
```bash
ssh -vvv -i ~/.ssh/devops_vm -p 2222 devops@127.0.0.1 2>&1 | grep -i "authentications that can continue"
```
Сейчас будет `publickey,password` (после задания 2 — только `publickey`).

> 📸 **S13 (обязательно)** — строка `Authentications that can continue: publickey,password`.
> *Подпись:* «Методы аутентификации до усиления защиты: publickey,password».

### Шаг 1.6 — `~/.ssh/config`

🍎 **MAC**
```bash
nano ~/.ssh/config
```
Вставь (сохранить: `Ctrl+O`, Enter, выйти: `Ctrl+X`):
```
Host devops
    HostName 127.0.0.1
    Port 2222
    User devops
    IdentityFile ~/.ssh/devops_vm
    IdentitiesOnly yes
```
Если файл уже существовал — **добавь блок в конец**, старое не стирай. Права: `chmod 600 ~/.ssh/config`.

`IdentitiesOnly yes` — предъявлять только указанный ключ. Без него клиент перебирает все ключи подряд, а при `MaxAuthTries 3` (задание 2) лимит попыток может кончиться до нужного ключа.

Проверка:
```bash
ssh devops
```

> 📸 **S14** — `cat ~/.ssh/config` и успешный `ssh devops` без пароля.

**Снимок состояния:** на выключенной (или работающей) ВМ → Снимки → **`02-keys-configured`**.

> 📸 **S15** — менеджер снимков (две записи).

## 4. Задание 2. Усиление защиты SSH

> **Правило:** окно №1 с SSH-сессией **не закрывать** до конца задания. Все проверки — в **новом** окне Терминала (окно №2).

### Шаг 2.1 — резервная копия и drop-in файл

🔐 **VM по SSH** (окно №1: `ssh devops`)
```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.backup
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```
Содержимое:
```
Port 2222

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
MaxAuthTries 3
LoginGraceTime 30

AllowUsers devops

X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
```

**Что значат директивы (для объяснения в отчёте):**

| Директива | Смысл |
|---|---|
| `Port 2222` | нестандартный порт — снижает «шум» от ботов, но защитой не является |
| `PermitRootLogin no` | вход напрямую под root запрещён |
| `PasswordAuthentication no` | только ключи, перебор пароля невозможен |
| `PubkeyAuthentication yes` | вход по ключу разрешён |
| `PermitEmptyPasswords no` | пустые пароли запрещены |
| `MaxAuthTries 3` | максимум 3 попытки аутентификации за соединение |
| `LoginGraceTime 30` | 30 секунд на вход, потом соединение закрывается |
| `AllowUsers devops` | входить по SSH может только `devops` (теперь `student` по SSH не войдёт, только через консоль ВМ — так и задумано) |
| `X11Forwarding no` | отключена передача графики |
| `ClientAliveInterval 300` / `CountMax 2` | неактивная сессия рвётся примерно через 10 минут |

**Подвох Ubuntu 24.04: конфликт с cloud-init.** В `/etc/ssh/sshd_config.d/` может лежать `50-cloud-init.conf` с `PasswordAuthentication yes`. Файлы читаются по алфавиту и **побеждает первое встреченное значение**, поэтому `99-…` его не переопределит. Проверка (обязательно с `sudo`, иначе файл не прочитается, и проверка будет неполной):

```bash
sudo grep -r "PasswordAuthentication" /etc/ssh/sshd_config.d/ /etc/ssh/sshd_config
```
Если найдена строка `PasswordAuthentication yes` в `50-cloud-init.conf` — закомментировать:
```bash
sudo sed -i 's/^PasswordAuthentication yes/#PasswordAuthentication yes/' /etc/ssh/sshd_config.d/50-cloud-init.conf
```

> 📸 **S16** — вывод `grep -r "PasswordAuthentication"` с конфликтной строкой (если она есть у тебя — отличный материал для раздела «затруднения»). Если файла нет — скриншот без конфликта тоже годится, напиши об этом.

### Шаг 2.2 — синтаксис и действующие значения

🔐 **VM**
```bash
sudo sshd -t && echo "Конфигурация корректна"
sudo sshd -T | grep -Ei "^(port|permitrootlogin|passwordauthentication|maxauthtries|allowusers)"
```
`sshd -T` показывает **реальные** итоговые значения; читать файлы глазами ненадёжно из-за переопределений. Ожидается: `port 2222`, `permitrootlogin no`, `passwordauthentication no`, `maxauthtries 3`, `allowusers devops`.

> 📸 **S17 (обязательно)** — вывод `sshd -t` и `sshd -T | grep ...`.

### Шаг 2.3 — порт и ssh.socket

🔐 **VM**
```bash
sudo systemctl disable --now ssh.socket
sudo systemctl enable --now ssh.service
sudo systemctl restart ssh
sudo ss -tlnp | grep sshd
```
Ожидается `0.0.0.0:2222` (и `[::]:2222`). Если остался `:22` — значит `ssh.socket` перекрывает директиву `Port`.

> 📸 **S18 (обязательно)** — вывод `ss -tlnp | grep sshd` с портом 2222.
> *Подпись:* «sshd слушает 0.0.0.0:2222; порт 22 не прослушивается. В Ubuntu 24.04 порт задаёт юнит ssh.socket, поэтому он отключён, а запуск переведён на ssh.service».

> Окно №1 при этом **не закрывается** — действующее соединение живёт.

### Шаг 2.4 — обновить проброс порта

VirtualBox → Настройки → Сеть → Адаптер 1 → Проброс портов → правило `ssh`: **порт гостя 22 → 2222** (порт хоста остаётся 2222). Можно менять и на работающей ВМ.

### Шаг 2.5 — проверки (окно №2, 🍎 MAC!)

## 5. Задание 3. Межсетевой экран (UFW)

> **Порядок критичен.** Если включить файрвол с `deny incoming` до разрешающего правила для SSH-порта, соединение оборвётся. Сначала правила, потом `enable`.

### Шаг 3.1 — политики и правила

🔐 **VM**
```bash
sudo ufw status verbose                  # ожидается Status: inactive
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 2222/tcp comment 'SSH'
sudo ufw allow 80/tcp  comment 'HTTP'    # понадобится в работе № 6
sudo ufw allow 443/tcp comment 'HTTPS'
```
**Не использовать `ufw allow ssh`:** имя `ssh` переводится в номер порта по файлу `/etc/services` (там 22), а не по конфигурации sshd (у нас 2222). Получится правило для 22, а в `ufw status` создастся ложная уверенность, что SSH разрешён.

### Шаг 3.2 — включить (окно №1 не закрывать)

```bash
sudo ufw enable
sudo ufw status numbered
```
Подтверди `y`. Затем в окне №2 (🍎 MAC) проверь, что новое подключение `ssh devops` работает.

### Шаг 3.3 — limit вместо allow для SSH

🔐 **VM**
```bash
sudo ufw delete allow 2222/tcp
sudo ufw limit 2222/tcp comment 'SSH rate-limited'
sudo ufw status verbose
```
`limit` разрешает соединения, но блокирует источник, который открыл **6 и более соединений за 30 секунд** — защита от подбора. В выводе правило помечено `LIMIT`. Побочный эффект: если часто и быстро запускать `ssh` подряд, можно временно заблокировать самого себя. Не спамь подключениями, особенно в скриптах.

> 📸 **S22 (обязательно)** — `ufw status verbose`: `Status: active`, `Default: deny (incoming), allow (outgoing)`, правило `2222/tcp LIMIT IN`, `80/tcp` и `443/tcp` ALLOW IN.

### Шаг 3.4 — журнал заблокированного

🔐 **VM**
```bash
sudo ufw logging medium
```
🍎 **MAC**
```bash
curl -m 3 http://192.168.56.101:8080
```
Ожидается таймаут: `curl: (28) Connection timed out after 3001 milliseconds` — пакеты молча отбрасываются (DROP), отказа клиент не получает.

🔐 **VM**
```bash
sudo grep 'UFW BLOCK' /var/log/ufw.log | tail -5
```
Пример записи и разбор:
```
... [UFW BLOCK] IN=enp0s8 OUT= MAC=... SRC=192.168.56.1 DST=192.168.56.101 ... PROTO=TCP SPT=53886 DPT=8080 ... SYN
```
- `SRC` — адрес отправителя (твой Mac в сети Host-only, `192.168.56.1`);
- `DST` — адрес назначения (сервер `192.168.56.101`);
- `PROTO` — протокол (`TCP`);
- `DPT` — порт назначения (`8080`, закрытый файрволом);
- дополнительно: `IN=` — интерфейс, через который пришёл пакет; `SPT` — случайный порт клиента; `SYN` — первый пакет установки TCP-соединения. Несколько записей подряд — повторные попытки (ретрансляции SYN).

> 📸 **S23 (обязательно)** — два окна рядом или два скриншота: `curl` с таймаутом (Mac) и записи `UFW BLOCK` в логе (VM).
> **Письменно в отчёт:** разбор полей `SRC/DST/PROTO/DPT` (текст выше).

**Материалы к отчёту по заданию 3:** S22, S23 + разбор записи.

## 6. Задание 4. Локальное доменное имя

### Шаг 4.1 — `/etc/hosts` на Mac

🍎 **MAC**
```bash
sudo nano /etc/hosts
```
Добавь **в конец**, остальное не трогай:
```
192.168.56.101   devops.local
```
(IP — твой реальный адрес Host-only из `ip -brief address`.)

Сброс кэша DNS на macOS:
```bash
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
```
Проверка:
```bash
ping -c 4 devops.local
ssh -p 2222 devops@devops.local
```
> Особенность macOS: зона `.local` обычно обслуживается Bonjour/mDNS. Запись из `/etc/hosts` всё равно срабатывает, но иногда `ping`/`ssh` по `.local` начинают с паузы в несколько секунд — это нормально.

Первое подключение по имени может завершиться `Permission denied (publickey)`: блок `Host devops` в `~/.ssh/config` относится только к псевдониму `devops`, а для `devops.local` ключ не предъявляется. Подключись с ключом явно:
```bash
ssh -i ~/.ssh/devops_vm -p 2222 devops@devops.local
```
(Клиент может сообщить `known by the following other names: [127.0.0.1]:2222` — это тот же ключ хоста, всё хорошо.)

Чтобы работала короткая команда `ssh devops.local`, добавь в `~/.ssh/config` второй блок:
```
Host devops.local
    Port 2222
    User devops
    IdentityFile ~/.ssh/devops_vm
    IdentitiesOnly yes
```
Теперь:
```bash
ssh devops.local
```
В VM после входа `last` / сообщение «Last login … from 192.168.56.1» показывает, что соединение шло напрямую по Host-only, а не через NAT-проброс (там источник был бы `10.0.2.2`).

> 📸 **S24 (обязательно)** — `ping -c 4 devops.local` + `ssh devops.local` (или `ssh ... devops@devops.local`) — вход выполнен.

### Шаг 4.2 — FQDN сервера

sudo sed -i 's/^127.0.1.1.*/127.0.1.1 devops-vm.devops.local devops-vm/' /etc/hosts

### 8.2 `scripts/audit.sh` — три TODO реализованы

🍎 **MAC**
```bash
cat > scripts/audit.sh <<'EOF'
#!/usr/bin/env bash
set -uo pipefail

PASS=0; FAIL=0

check() {
    local desc="$1" expected="$2" actual="$3"
    if [[ "$actual" == "$expected" ]]; then
        echo "  [OK]   $desc"; ((PASS++))
    else
        echo "  [FAIL] $desc (ожидалось: '$expected', получено: '$actual')"; ((FAIL++))
    fi
}

echo "Аудит конфигурации: $(hostname -f), $(date '+%Y-%m-%d %H:%M')"

echo "[1] Служба SSH"
check "Вход от имени root запрещён"        "no"  "$(sudo sshd -T | awk '/^permitrootlogin/{print $2}')"
check "Парольная аутентификация отключена" "no"  "$(sudo sshd -T | awk '/^passwordauthentication/{print $2}')"
# TODO 1: порт SSH отличен от 22
ssh_port="$(sudo sshd -T | awk '/^port/{print $2}' | head -n1)"
if [[ "$ssh_port" != "22" ]]; then port_is_custom="yes"; else port_is_custom="no"; fi
check "Порт SSH отличен от 22 (текущий: $ssh_port)" "yes" "$port_is_custom"
# TODO 2: MaxAuthTries равно 3
check "MaxAuthTries равно 3" "3" "$(sudo sshd -T | awk '/^maxauthtries/{print $2}')"

echo "[2] Межсетевой экран"
check "Межсетевой экран активен" "active" "$(sudo ufw status | awk '/^Status:/{print $2}')"
# TODO 3: политика по умолчанию для входящего трафика равна deny
check "Политика по умолчанию для входящих: deny" "deny" \
      "$(sudo ufw status verbose | grep '^Default' | sed -E 's/^Default: ([a-z]+) \(incoming\).*/\1/')"

echo "[3] Учётные записи"
awk -F: '$3>=1000 && $3<65534 {printf "    %s (uid=%s)\n",$1,$3}' /etc/passwd

echo "Пройдено: $PASS, не пройдено: $FAIL"
[[ $FAIL -eq 0 ]] && exit 0 || exit 1
EOF
chmod +x scripts/audit.sh
```

**Как работает (для отчёта):** функция `check` сравнивает ожидаемое и фактическое значение, печатает `[OK]/[FAIL]` и считает итог; значения берутся из `sshd -T` и `ufw status verbose`, а не из файлов (в файлах директивы могут быть переопределены). Код возврата 0 — всё хорошо, 1 — есть нарушения; **ненулевой код нужен, чтобы в работе № 10 прерывать CI-конвейер**.

## 9. Аварийный выход (если потерял доступ)

| Симптом | Причина | Что делать |
|---|---|---|
| `Connection refused` на 2222 | sshd не слушает этот порт (ошибка конфига / ssh.socket / не обновлён проброс VirtualBox) | войти в **консоль ВМ** под `student`; `sudo sshd -t`, `sudo ss -tlnp \| grep sshd`, проверить проброс порта |
| `Connection timed out` | UFW блокирует (нет правила на 2222) или вы в блокировке `limit` | консоль ВМ: `sudo ufw status numbered`, `sudo ufw allow 2222/tcp` или `sudo ufw disable`; подождать 30 с |
| `Permission denied (publickey)` для `devops` | неправильные права на `~/.ssh`, не тот ключ, `AllowUsers` | консоль ВМ: `sudo chmod 700 /home/devops/.ssh; sudo chmod 600 /home/devops/.ssh/authorized_keys; sudo chown -R devops:devops /home/devops/.ssh` |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | пересоздана ВМ / другой хост на этом адресе | **сначала** сверить отпечаток через консоль ВМ (`sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), и только потом `ssh-keygen -R "[127.0.0.1]:2222"` |
| `UNPROTECTED PRIVATE KEY FILE` | у ключа широкие права | `chmod 600 ~/.ssh/devops_vm` |
| Не зайти даже через консоль / всё сломано | — | восстановить ВМ из снимка (Снимки → правый клик → Восстановить) |

Консольный вход (окно VirtualBox) **не зависит от sshd и UFW** — он всегда остаётся запасным путём.

## 12. Контрольные вопросы — основа для ответов

*(Своими словами подгони под свой отчёт, добавь свои цифры/наблюдения.)*

**1. NAT vs Host-only: входящее соединение.**
При NAT гипервизор работает как маршрутизатор с трансляцией адресов: гость в закрытой сети `10.0.2.0/24`, у него нет адреса, достижимого извне. Исходящее соединение создаёт запись в таблице трансляции, ответы возвращаются по ней; для входящего такой записи нет, поэтому нужен проброс портов. Host-only — изолированный сегмент (`192.168.56.0/24`), в который входят и хост (`192.168.56.1`), и гость; трансляции нет, узлы видят друг друга напрямую (но в Интернет доступа нет).

**2. `known_hosts` и `authorized_keys`.**
`~/.ssh/known_hosts` — на **клиенте** (Mac): отпечатки ключей серверов, к которым уже подключались; защищает от подмены сервера (аутентификация сервера клиентом). `~/.ssh/authorized_keys` — на **сервере**, в домашнем каталоге пользователя: открытые ключи клиентов, допущенных ко входу (аутентификация клиента сервером).

**3. Ключ лучше пароля, хотя канал защищён.**
Шифрование защищает от перехвата, но не от остальных проблем пароля: он передаётся серверу (его видит подменённый или скомпрометированный сервер), его можно угадать, перебрать, повторно использовать на других сервисах, он утекает при фишинге. Закрытый ключ с клиента не уходит: клиент лишь подписывает данные сессии. Перебор ed25519 практически невозможен, доступ отзывается удалением одной строки из `authorized_keys`, ключ можно защитить парольной фразой.

**4. `ufw allow` и `ufw limit`.**
`allow` разрешает соединения без ограничений. `limit` тоже разрешает, но блокирует источник, который за 30 секунд инициировал 6 и более соединений, — защита от подбора паролей и массовых попыток подключения.

**5. После правки `sshd_config` — `Connection refused`.**
Нарушена процедура: сессию закрыли, не проверив, что служба поднялась и принимает новые соединения. `Connection refused` значит, что на порту никто не слушает (служба упала из-за ошибки конфигурации или слушает другой порт). Помогли бы: `sudo sshd -t` (до перезапуска) и `sudo ss -tlnp | grep sshd` + проверка нового подключения в отдельном окне, не закрывая старое.

**6. `ufw default deny incoming`, `ufw enable`, `ufw allow 22/tcp`.**
Первая команда лишь меняет политику, пока экран выключен. Проблема наступает на `ufw enable`: фильтр включён, а разрешающего правила SSH ещё нет, новые входящие соединения блокируются (уже установленная сессия иногда выживает, но новую не открыть). Правильно: `default deny incoming` → `default allow outgoing` → `allow <порт SSH>/tcp` → `enable`, затем проверка новым соединением.

**7. `ufw allow ssh` при порте 2222.**
UFW переводит имя `ssh` в номер порта по `/etc/services` (там 22/tcp), а не по конфигурации sshd. Создаётся правило для 22, оно видно в `ufw status`, но реальный порт 2222 закрыт политикой deny.

**8. «Смена порта — security through obscurity».**
Отчасти верно: целенаправленный атакующий найдёт порт сканированием (nmap, masscan) за минуты, сама служба и её уязвимости остаются теми же, замены ключам/запрету root/пароля это не даёт. Но мера решает практическую задачу: большинство автоматических ботов бьёт только в порт 22, поэтому журнал меньше засоряется, меньше нагрузка и случайных попыток подбора, проще заметить реальные аномалии. Это вспомогательная мера, а не защита.

**9. `REMOTE HOST IDENTIFICATION HAS CHANGED`.**
Причины: 1) сервер переустановлен/ключи хоста перегенерированы; 2) по этому адресу/имени/пробросу теперь другая машина (смена IP по DHCP, другая ВМ); 3) атака «человек посередине». Различить: получить отпечаток ключа по независимому доверенному каналу (консоль ВМ/провайдера: `sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), сравнить с предъявленным, выяснить у администраторов, были ли переустановка или миграция. `ssh-keygen -R` «вслепую» некорректно: команда просто удаляет запись, при следующем подключении привычно принимается новый отпечаток, возможно подменный, и защита от подмены сервера обнуляется. Использовать только после сверки отпечатка.

**10. Права на закрытый ключ.**
Клиент отказывается использовать ключ, доступный группе/другим (`UNPROTECTED PRIVATE KEY FILE`). Закрытый ключ — по сути удостоверение владельца: у кого есть копия, тот входит на все серверы с соответствующим открытым ключом. Даже если файл «свой», он может читаться другими локальными пользователями/процессами, утечь через общие каталоги, резервные копии или после копирования (флешка, архив — права часто сбрасываются). Защита от локальных угроз. Правильные права: 600 на файл, 700 на `~/.ssh`.

**11. `ping myapp.local` работает, `dig myapp.local` пусто.**
`ping` использует системное разрешение имён (`getaddrinfo`) по директиве `hosts:` в `/etc/nsswitch.conf`, то есть читает и `/etc/hosts`. `dig` обращается напрямую к DNS, минуя `nsswitch` и `/etc/hosts`; в DNS записи нет — ответ пуст. Противоречия нет. Порядок: приложение → библиотека → `/etc/nsswitch.conf` (`hosts:`) → 1) `/etc/hosts` (статические записи, без кэша и TTL) → 2) локальный резолвер `systemd-resolved` (`127.0.0.53:53`, кэш) → 3) внешние DNS-серверы (по DHCP или статически).

**12. `ssh -L 9090:127.0.0.1:8080 user@server`.**
Адрес `127.0.0.1` интерпретируется **в адресном пространстве сервера**: порт 9090 открывается на клиенте, а `sshd` на сервере сам подключается к своему loopback `:8080`. Файрвол не мешает, потому что весь трафик идёт внутри уже разрешённого зашифрованного SSH-соединения (порт 2222), а последний участок проходит по интерфейсу `lo` внутри сервера, куда правила входящего трафика не применяются.

**13. Достаточно ли журнала `sudo`, если можно `sudo su -`?**
Нет. `sudo su -` (как `sudo -i`, `sudo bash`) открывает оболочку root; в `/var/log/auth.log` попадёт только запуск оболочки, а дальнейшие команды выполняются от root и не привязаны к конкретному администратору. Решения: ограничить в `visudo` список разрешённых команд и запретить оболочки; включить журналирование ввода-вывода сессий sudo (`Defaults log_input, log_output`); использовать `auditd` с правилами на `execve` (сохраняется исходный `auid`); централизованный сбор логов.

**14. Три недостатка ручной настройки при многих узлах.**
1) Дрейф конфигурации — серверы со временем начинают отличаться («серверы-снежинки»); 2) плохая масштабируемость — каждое действие повторяется на каждом узле, время и число ошибок растут; 3) невоспроизводимость и слабый аудит — нет декларативного описания и истории изменений, трудно восстановить узел после сбоя или проверить соответствие требованиям. Ansible даёт идемпотентность, повторяемость и хранение конфигурации в Git.
